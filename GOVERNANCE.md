GOVERNANCE.md
HUNTIQ‑V5 — Doctrine MAX ULTRA + BCE‑4X + Steeve MAX
Version institutionnelle — Inviolable, non‑négociable, permanente
1. Mission du dépôt
HUNTIQ‑V5 est la version active, scientifique et opérationnelle du système HUNTIQ.
Ce dépôt est régi par une gouvernance stricte visant à :

éliminer toute régression,

garantir la traçabilité totale,

protéger l’intégrité scientifique,

maintenir une architecture stable,

encadrer strictement les contributions humaines et automatisées.

Cette gouvernance est obligatoire, non modifiable, non interprétable.

2. Structure des branches
2.1 Branches institutionnelles
main

Branche mère.

Contient la gouvernance, les protocoles, les standards.

Ne reçoit aucun développement direct.

Ne reçoit que des PR validées et certifiées.

bionic‑v3‑dev-safepoint

Coffre‑fort inviolable.

Aucun commit direct.

Aucun merge direct.

Sert de point de restauration absolu.

2.2 Branches actives
bionic‑v3‑dev

Seule branche autorisée pour le développement actif.

Toutes les contributions d’Emergent doivent aller ici.

Toutes les évolutions doivent être traçables et justifiées.

3. Règles de contribution
3.1 Interdictions absolues
Aucun commit direct dans main.

Aucun commit direct dans bionic‑v3‑dev-safepoint.

Aucun fichier supprimé sans justification écrite.

Aucun renommage massif sans protocole.

Aucun changement d’architecture sans validation.

Aucun contournement de BCE‑4X.

3.2 Obligations
Chaque commit doit être justifié, clair, traçable.

Chaque modification doit être réversible.

Chaque évolution doit respecter la structure existante.

Chaque PR doit inclure :

description,

justification,

impact,

risques,

plan de rollback.

4. Doctrine BCE‑4X
BCE‑4X est le pare‑feu anti‑régression du projet.
Il impose :

validation systématique,

audit continu,

justification écrite,

interdiction de modifier les zones gelées,

traçabilité totale des décisions.

Toute violation de BCE‑4X entraîne :

rejet automatique de la PR,

restauration immédiate,

documentation obligatoire de l’incident.

5. Doctrine Steeve MAX
Steeve MAX impose :

zéro ambiguïté,

zéro interprétation,

zéro improvisation,

zéro modification non documentée,

zéro impact non mesuré.

Les contributions doivent être :

explicites,

propres,

cohérentes,

alignées sur la vision,

conformes à l’architecture.

6. Règles pour Emergent
Emergent doit :

travailler uniquement dans bionic‑v3‑dev,

respecter BCE‑4X,

respecter Steeve MAX,

produire des commits propres,

documenter chaque action,

ne jamais modifier main,

ne jamais toucher au safepoint.

Toute déviation entraîne :

rollback immédiat,

verrouillage temporaire,

audit obligatoire.

7. Règles de merge
Toute PR vers main doit être approuvée manuellement.

Toute PR doit être testée, auditée, validée.

Aucun merge automatique n’est autorisé.

Aucun fast‑forward n’est autorisé.

Les merges doivent être explicites et documentés.

8. Règles de sécurité
Aucun secret dans le code.

Aucun token en clair.

Aucun accès non documenté.

Aucun fichier sensible dans le dépôt.

Audit régulier obligatoire.

9. Règles de documentation
Toute fonctionnalité doit être documentée.

Toute architecture doit être décrite.

Toute évolution doit être expliquée.

Toute décision doit être justifiée.

10. Caractère inviolable
Ce document est :

permanent,

non modifiable sans PR formelle,

non interprétable,

non négociable.

Il constitue la loi interne de HUNTIQ‑V5.

Fin du document.
